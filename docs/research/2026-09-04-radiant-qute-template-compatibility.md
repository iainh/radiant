# Research: Radiant and Qute template compatibility

**Date**: 2026-09-04
**Question**: Where does Radiant's template support or syntax differ from Quarkus Qute, and what should be done about each difference?
**Status**: Complete

## Scope

This compares the current Radiant `main` branch with the current Quarkus Qute reference language. It covers syntax, expression semantics, sections, composition, output handling, extension points and compile-time checking. Java- and Quarkus-specific facilities are included only when there is a useful Rust analogue. CDI, Java reflection, Jandex, Mutiny types and Jakarta REST APIs are not compatibility targets.

The primary Qute source is the [Qute reference guide](https://quarkus.io/guides/qute-reference), supplemented by the current Qute core implementation and tests in [`quarkusio/quarkus`](https://github.com/quarkusio/quarkus/tree/main/independent-projects/qute/core).

Effort estimates are relative:

- **S**: localized parser or evaluator work;
- **M**: cross-cutting parser/evaluator/tests or a modest new API;
- **L**: new architecture, code generation or policy surface.

## Summary

Radiant implements the centre of Qute's language: output expressions, strict missing-value handling, explicit safe/default operations, lexical scopes, the principal control-flow sections, include/insert inheritance, external fragments, isolated tag templates, async resolvers, variants and content-type escaping. The matching names conceal important incompatibilities, however.

The first priority should be a **Qute-compatible core profile**, not implementation of every Quarkus integration. The profile should fix constructs that currently parse but produce the wrong result: `else if`, same-template fragment includes, tag arguments and nested content, dynamic fragment visibility, safe indexed/call expressions, parameter defaults, and section argument spacing. Parser compatibility for literal braces, multi-pipe raw blocks and standalone lines should follow. These changes are mostly small or medium and provide more migration value than `eval`, caching or framework namespaces.

Radiant should retain deliberate Rust differences: explicit model exposure rather than reflection, media-specific trusted wrappers rather than a universal `.raw`, Rust futures/streams rather than `CompletionStage`/`Uni`, and explicit registration rather than CDI or global discovery.

## Compatibility gaps to fix

These are likely to surprise someone porting a Qute template because Radiant accepts the same or very similar spelling but rejects it later or gives a different result.

| Area | Current difference and impact | Resolution | Disposition / effort |
| --- | --- | --- | --- |
| `else if` | Qute represents `{#else if condition}` as another conditional block and permits a chain. Radiant parses the block arguments but [`render_section()`](../../src/engine.rs#L477-L489) ignores them and renders the first `else` unconditionally. | Preserve each `else` block's optional `if` expression and evaluate blocks in order. Generate equivalent direct-renderer code. Validate malformed and duplicate terminal `else` blocks. | **Fix; S–M.** This is wrong-result compatibility, so it is highest priority. |
| Safe suffix over index/call | Qute's terminal `??` recovers from a not-found anywhere in the expression chain. Radiant's index and call paths use [`required()`](../../src/engine.rs#L881-L903), converting not-found into an error before the surrounding [`Expr::Safe`](../../src/engine.rs#L913-L917) can see it. `{missing[0]??}` and safe calls therefore still fail. | Keep `Resolution` through index and callee-base evaluation; require arguments only when invocation actually proceeds. Apply strict failure only after the complete output/section expression is evaluated. | **Fix; M.** Add chain conformance tests. |
| Section argument tokenization | Qute accepts spaces on either side of `=`. Radiant splits arguments on whitespace first, so forms such as `name = 'Ada'` become multiple arguments ([`split_arguments()`](../../radiant-compiler/src/parser.rs#L411-L447)). | Replace splitting plus `top_level_equals()` with one quote/bracket-aware section-parameter scanner that assembles `name`, `=` and value while retaining spans. | **Fix; M.** Important for copying ordinary Qute templates. |
| Same-template fragments | Qute `{#include $card /}` means fragment `card` in the current template. Radiant splits at `$`, then attempts to normalize an empty template ID ([`render_include()`](../../src/engine.rs#L688-L695)). | Treat an empty pre-`$` ID as the current template ID. Ensure cycle keys still include the fragment and teach the checked dependency loader not to load an empty path. | **Fix; S.** |
| Fragment visibility | In Qute, `rendered=` is evaluated per render; `_hidden` is a marker; `capture` defines a retrievable hidden fragment. Radiant only recognizes literal `rendered=false`, requires `_hidden` to look like a named argument, and makes `capture` a no-op that is not indexed as a fragment ([`engine.rs`](../../src/engine.rs#L530-L547), [`ast.rs`](../../radiant-compiler/src/ast.rs#L34-L51)). | Normalize `capture` to a hidden fragment in the AST, validate its ID, evaluate `rendered` truthiness dynamically, recognize a bare `_hidden`, and always render a fragment when explicitly selected/included. | **Fix; M.** |
| Fragment namespaces/options | Qute supports `frg:`/`fragment:` and `cap:`/`capture:` output plus `_ignoreFragments=true`. Radiant has neither and always interprets `$` as a fragment separator. | Add engine-owned fragment namespace resolvers that render in the current state, and honour `_ignoreFragments`. This may require a resolver result that can carry trusted rendered output without losing media semantics. | **Add after core fragment fix; M.** Namespace rendering is useful; `_ignoreFragments` is low priority unless `$` is needed in IDs. |
| User tag arguments | Qute binds the first unnamed argument as `it`, defaults simple unnamed arguments to a same-named binding, and exposes `_args`. Radiant's [`include_parameters()`](../../src/engine.rs#L790-L809) discards all unnamed arguments, so the common `{#itemDetail item}` form loses `item`. | Create a distinct tag-call argument normalizer: evaluate positional/named arguments, bind `it`, add default names for simple identifiers/string words, and construct `_args` metadata. Implement `_args` basics first (`size`, lookup, iteration); filters and `asHtmlAttributes` can follow. | **Fix core `it`; S–M. Add full `_args`; M.** |
| User tag body and isolation opt-out | Qute exposes the caller body as `nested-content` and through an unnamed `insert`; `_isolated=false` or `_unisolated` restores caller lookup. Radiant supports insert overrides, but not `nested-content`, and `tag || …` makes every tag permanently isolated ([`engine.rs`](../../src/engine.rs#L751-L763)). | Preserve the existing insert mechanism, add a rendered nested-content binding, and calculate isolation from Qute's two opt-outs. Evaluate nested content in the caller context with tag arguments visible. | **Fix; M.** |
| Checked tag dependencies | Unknown sections are dynamically mapped to `tags/<name>`, but [`Template::dependencies()`](../../radiant-compiler/src/ast.rs#L10-L31) records only explicit includes. A checked template using a tag therefore does not embed or validate its tag template unless it is separately registered. | Distinguish registered/built-in sections from tag calls during macro graph loading, resolve `tags/<name>` with suffixes, and include tag dependencies and cycles. | **Fix; M.** Required before claiming checked tag support. |
| Unknown sections | Qute knows which user tags/custom helpers are registered. Radiant treats every unrecognized section as a tag ([`engine.rs`](../../src/engine.rs#L547-L550)), turning typos and unsupported built-ins into late missing-template errors. | Build a tag registry from registered/located `tags/` templates, or at minimum test for a resolvable tag and return `UnknownSection` with the original source span. A future custom-section registry should share this name table. | **Fix; M.** Improves diagnostics and checked dependency analysis. |
| Parameter declaration defaults | Qute supports `{@Type name=expression}` and uses the default for null/not-found. Radiant only accepts exactly two whitespace-separated tokens and discards declarations during rendering ([`parser.rs`](../../radiant-compiler/src/parser.rs#L253-L267), [`engine.rs`](../../src/engine.rs#L427-L430)). | Extend `Parameter` with an optional expression and lower defaults to lexical `name?=default` semantics at template/containing-section scope. Validate assignability where the checked path has Rust type information. | **Fix; M.** Existing no-default declarations can remain metadata. |
| `let` conditional assignment | Qute `enabled?=true` retains an outer non-null value and otherwise supplies the default. Radiant treats the literal key `enabled?` as a separate local. | Represent conditional assignment explicitly, look up the unsuffixed outer key, and bind either that value or the evaluated default. | **Fix with parameter defaults; S.** |
| Fragment IDs and graph validation | Qute enforces alphanumeric/underscore fragment IDs and validates checked fragment references. Radiant validates IDs only in `DynamicTemplate::fragment()`, not declarations; its macro loads the referenced template but does not verify the fragment exists ([`parser.rs`](../../radiant-compiler/src/parser.rs#L493-L503), [`lib.rs`](../../radiant-macros/src/lib.rs#L493-L500)). | Validate declaration IDs in the compiler, verify static `$fragment` targets after graph loading, and validate insert override names against target inserts where statically knowable. | **Fix; S–M.** |
| Non-strict output | With strict rendering disabled, Qute outputs `NOT_FOUND` by default and offers configurable strategies. Radiant silently emits nothing ([`engine.rs`](../../src/engine.rs#L437-L445)). | Either match Qute's default and add a strategy enum, or explicitly define Radiant's blank output as a divergence. Avoid a bare boolean once compatibility modes exist. | **Decide before stabilizing API; S.** Prefer an enum with strict as the default. |

## Missing core language features

These features are absent rather than incorrectly implemented.

| Area | Qute capability / Radiant gap | Resolution | Disposition / effort |
| --- | --- | --- | --- |
| `with` | Qute evaluates once and changes `this`/current context. Radiant has no `with`; it is currently mistaken for a tag. | Push the evaluated value as a scope/current context for the body, then pop it. Ensure unqualified lookup starts on object-like values, not only maps, if Radiant later gains opaque values. | **Add; S.** Useful and easy, though `let it=…` remains clearer for checked templates. |
| Optional section end tags | Qute lets `let`/`set` and `include` end at their parent boundary. Radiant requires every non-self-closing section to close ([`parser.rs`](../../radiant-compiler/src/parser.rs#L154-L160)). | Give section definitions a missing-end strategy and unwind only helpers that bind to their parent. Do not auto-close `if`, `for`, `when`, `with` or fragments. | **Add for migration compatibility; M.** Explicit closure is arguably clearer, so this could instead remain a documented parser-profile choice. |
| Loop inputs | Qute iterates iterables, iterators, arrays, maps, streams and positive integers (1…n). Radiant accepts only `Sequence`, `Map` and `Null` ([`engine.rs`](../../src/engine.rs#L577-L597)). | Add integer iteration cheaply. Supporting lazy/async iterables requires expanding `Value` or resolver contracts and should be designed with streaming. Rust arrays/slices already become sequences through `IntoValue`. | **Integer: S. Lazy/async iterables: L.** |
| Loop metadata | Radiant has `index`, `count`, `isFirst`, `isLast`, `hasNext`; Qute also has `odd`, `even`, `indexParity` and configurable prefixes. | Add the three missing values to both evaluator and direct compiler. Add builder prefix configuration only if migration demand warrants it. | **Metadata: S. Prefix configuration: S–M.** |
| Rich `when` cases | Radiant supports equality only ([`engine.rs`](../../src/engine.rs#L624-L649)). Qute supports inequality, ordering, `in`, not-in and enum-like raw constants. | Parse case conditions into a dedicated match predicate instead of ordinary expression arguments; reuse comparison logic and support raw identifiers for enum/string matching. | **Add; M.** High value for Qute migration. |
| Expression aliases/infix | Qute supports textual condition aliases (`eq`, `is`, `ne`, `gt`, `ge`, `lt`, `le`, `and`, `or`), Elvis as `or`/`.or()`, and arbitrary one-argument virtual methods in infix form. Radiant supports only symbolic operators and normal method-call syntax. | Add textual operator aliases first. General infix virtual methods make the grammar more ambiguous and should be behind a compatibility parser profile or deliberately omitted. | **Aliases: S–M. General infix: M; optional.** |
| Ternary and `orEmpty` | Qute has `condition ? yes : no` and null/not-found-to-empty `orEmpty`. Radiant has neither. | Add a ternary AST node with lazy branch evaluation. Add `orEmpty` as a built-in recovery member that can receive not-found, which likely benefits from the same evaluator refactor as safe chains. | **Add; M.** |
| Numeric literal suffixes / numeric dot index | Qute accepts Java numeric suffixes and `list.0`; Radiant has one integer and one float type and requires `list[0]`. | Do not add Java suffixes: they do not map usefully to Radiant's `i64`/`f64` model. Numeric dot indexing could be accepted as parser sugar. | **Omit suffixes; optional dot index S.** |
| Collection conveniences | Qute adds map `keySet`/`get`, list `reversed`/`take`/`takeLast`, plus formatting helpers. Radiant has a smaller set ([`engine.rs`](../../src/engine.rs#L1323-L1377)). | Add aliases (`keySet`) and `Map.get()` cheaply. Add non-mutating sequence operations where demand exists. Keep Java-specific formatting out of core; applications can register resolvers. | **Incremental; S each.** Do not pursue exhaustive Java parity. |
| Dynamic `eval` | Qute can parse and execute a string as a template when its helper is explicitly registered. Radiant has no eval. | If added, make it opt-in, disabled in restricted engines, count it against include depth/output limits, preserve source stack information and document that it reparses per call. | **Optional; M.** The original design intentionally deferred it because of security and policy cost. |
| Cached sections | Qute can cache a section's materialized result through an application cache. Radiant has no `{#cached}`. | Define an async cache trait supplied by the application; derive keys from template ID/source span/optional key; cache a media-specific rendered value; disable by default and in restricted mode. | **Optional; L.** Not a syntax priority. |
| Custom section helpers | Qute engines can register section helper factories and parser hooks. Radiant exposes value/namespace resolvers only; all section execution is hard-coded. | Add a section registry only after the built-in AST contracts stabilize. A custom helper needs parse-time shape validation, scope declarations, async rendering and checked-template visibility—not merely a runtime callback. | **Optional ecosystem feature; L.** |

## Lexical and whitespace differences

| Area | Current difference and impact | Resolution | Disposition / effort |
| --- | --- | --- | --- |
| Tag recognition | Qute only recognizes `{…}` as a tag when the first character is a letter/digit/underscore or command. JSON such as `{"foo":true}` and a tag with leading whitespace are literal. Radiant scans every `{`, trims the contents, and attempts expression parsing ([`parser.rs`](../../radiant-compiler/src/parser.rs#L61-L69), [`parser.rs`](../../radiant-compiler/src/parser.rs#L117-L151)). | Add Qute's tag-start predicate before looking for a close. Decide whether leading-space expressions should remain a Radiant extension; strict Qute mode should treat them as text. | **Fix/profile; S.** Prevents collisions with JSON, CSS and other brace syntax. |
| Literal brace escapes | Qute `\{` and `\}` output literal braces. Radiant has no template-level brace escaping. | Teach the text scanner to consume the escape backslash without opening/closing a tag. | **Add; S.** |
| Multi-pipe unparsed blocks | Qute supports `{||||…||||}` to allow `|}` in raw content. Radiant closes every raw block at the first `|}` ([`parser.rs`](../../radiant-compiler/src/parser.rs#L89-L105)). | Count the opening pipe run and require the same run before `}`. | **Add; S.** |
| Standalone lines | Qute removes section/comment/parameter-only lines by default. Radiant preserves all whitespace, as visible in checked rendering expectations ([`rendering.rs`](../../tests/rendering.rs#L30-L45)). | Add a parser option and source-to-AST whitespace pass. For Qute migration, default it on in a compatibility profile; changing Radiant's global default now would alter existing output. | **Add configurable behaviour; M.** |
| Identifier grammar | Qute expression identifiers are permissive non-whitespace parts (with Java identifiers recommended). Radiant starts identifiers with ASCII letters/underscore and only then allows Unicode alphanumerics ([`expr.rs`](../../radiant-compiler/src/expr.rs#L158-L175)). | Keep a documented Rust-like identifier grammar. Bracket lookup already handles arbitrary map keys. Optionally accept Unicode identifier starts using `is_alphabetic()`. | **Document; optional S.** Full non-whitespace identifiers would conflict with Radiant's operator grammar. |

## Checked-template and data-model gaps

| Area | Current difference and impact | Resolution | Disposition / effort |
| --- | --- | --- | --- |
| Completeness of compile-time expression checking | Qute checked templates validate all type-safe expressions and generated extensions. Radiant's direct compiler emits Rust field access only for simple member output/conditions/loops; any binary expression, call, index, namespace, safe/default, include or other section falls back to a dynamic `Value` map ([`radiant-macros`](../../radiant-macros/src/lib.rs#L234-L305), [`radiant-macros`](../../radiant-macros/src/lib.rs#L381-L405)). Those expressions are parsed at compile time but missing fields/type errors occur only at render time. | Be precise in documentation now. Longer term, separate typed name/accessor resolution from rendering so every checked expression can generate Rust type checks even if final execution uses the evaluator. Checked extension declarations also need a macro-visible registration mechanism. | **Document immediately; architectural fix L.** This is the largest substantive gap in Radiant's stated checked-template model. |
| Parameter declarations | Qute declarations drive type checking and generated resolvers. Radiant stores `type_name`/`name`, but neither compiler nor macro uses them ([`ast.rs`](../../radiant-compiler/src/ast.rs#L79-L84)). | For dynamic templates, treat them as schema metadata and optionally validate supplied values. For checked templates, reconcile declarations with derive fields or discourage redundant declarations. Do not attempt to resolve Java type names in Rust. | **Adapt; M–L.** |
| Type-safe fragment entry points | Qute can define checked methods/records for fragments. Radiant only has dynamic fragment selection; a checked template may include an external fragment but cannot expose a typed fragment renderer. | Add a fragment option to `#[template]` or generate fragment-specific methods whose argument structs define fragment data. Validate fragment existence and referenced fields. | **Useful; M–L.** |
| Deferred values | Qute transparently awaits `CompletionStage`/`Uni` values at any expression part. Radiant resolver methods are async, but `Value` cannot itself contain a future ([`value.rs`](../../src/value.rs#L5-L18)). | Add an owned, cancel-safe deferred value variant or a dedicated lazy resolver-backed object. Define memoization and repeat-render semantics before stabilizing it. Prefer handlers fetching business data explicitly. | **Optional; L.** Async resolvers cover many legitimate cases already. |
| Root object | Qute can render with one current root object. Radiant's dynamic `TemplateInstance` always constructs a named-data map ([`template.rs`](../../src/template.rs#L159-L190)). | Add `DynamicTemplate::data_root(Value)`/`TemplateInstance::root()` only if object-root templates are needed. Preserve named `.data()` as the ergonomic default. | **Optional; S–M.** |
| True output streaming | Qute can emit multiple materialized chunks. Radiant's Axum `stream()` defers rendering but emits exactly one fully buffered chunk ([`radiant-axum`](../../radiant-axum/src/lib.rs#L124-L159)). | Change the evaluator sink abstraction to support async chunk emission/backpressure, then expose a `Stream<Item = Result<Bytes, RenderError>>`. Keep buffered render as default. | **Gap; L.** This is runtime output support rather than syntax, but the current API name can imply more than it provides. |

## Deliberate or ecosystem-level differences

| Area | Difference | Recommendation | Effort |
| --- | --- | --- | --- |
| Raw/safe output | Qute exposes `.raw`/`.safe` and a universal `RawString`. Radiant requires `SafeHtml`, `SafeXml` or `SafeJsonString` from Rust ([`escape.rs`](../../src/escape.rs#L1-L27)). | **Keep Radiant's safer design.** If template-authored raw output is ever added, make it visibly unsafe and media-specific. Do not add a universal `.raw` merely for parity. | None; document migration. |
| Arithmetic and coercion | Radiant supports `*`, `/`, `%`, unary minus and mixed integer/float operations globally, while Qute's core language is resolver-oriented and Quarkus adds selected numeric/string extensions. Exact coercion and precedence can differ. | **Keep predictable Rust-oriented semantics.** Document them as Radiant syntax, test overflow/division, and avoid Java `BigDecimal` coercion unless a decimal value type is added. | Documentation/tests. |
| Media types and encodings | Qute variants can carry arbitrary content types and encodings; Radiant has four UTF-8 media enum values. | Generalize `MediaType` only when real integrations need custom MIME types. Preserve fixed, safe defaults meanwhile. | Optional M. |
| Escaped apostrophe bytes | Both HTML escape apostrophes, but exact entities may differ (`&#x27;` versus Qute escaper output). Browsers interpret them equivalently, but golden output may differ. | Document non-byte-identical escaping; do not chase entity spelling unless migration tests require exact output. | None/S. |
| Messages | Qute message bodies are full, named-parameter Qute templates with generated typed bundles and localized files. Radiant's `MessageBundle` uses positional `{0}` placeholders and doubled-brace escapes only ([`messages.rs`](../../src/messages.rs#L115-L170)). | Either rename/document this as a lightweight message formatter, or implement a separate checked message-bundle layer using Radiant's parser and named arguments. Add UTF-8 file loading and derives only if localization is a major product goal. | **Current syntax divergence; full parity L.** |
| Standard namespaces | Quarkus preconfigures `cdi`/`inject`, `global`, `config`, `str`, `time`, fragment and generated enum/static namespaces. Radiant only owns `data:` and lets applications register explicit namespace resolvers. | Keep CDI/injection omitted. Consider small optional `str`, `time` and config adapter crates/functions. Add fragment namespaces as core because they are part of composition. | S–M each; CDI intentionally omitted. |
| Model exposure | Qute may use reflection or generated Java member resolvers. Radiant requires `TemplateValue`, `Value` or explicit resolvers. | **Keep.** This is an idiomatic Rust safety boundary, not a gap. Continue supporting rename rules for migration. | None. |
| Discovery and live reload | Quarkus discovers, caches and watches templates/tags automatically. Radiant embeds checked graphs or uses explicit loaders/reload and no watcher ([`README`](../../README.md#L137-L156)). | Keep production registration explicit. A development watcher can be an optional tool that calls `reload` and invalidates reverse dependencies. | Optional M–L. |
| Timeouts | Qute has engine/instance render timeouts. Radiant delegates deadlines to Axum, so framework-neutral dynamic rendering has no built-in timeout. | Keep cancellation owned by the caller, but document it prominently and consider a framework-neutral deadline wrapper if non-Axum users need one. | Optional S–M. |
| `eval`, cache, parser hooks and debug mode | Qute makes these opt-in or integration features; Radiant's original design explicitly deferred them ([`design`](2026-09-04-radiant-qute-axum-design.md#L439-L453)). | Preserve the deferral until the compatibility-core issues above are resolved. | See feature rows above. |

## Recommended sequence

1. **Prevent wrong results**: implement `else if`; fix terminal `??` for index/call chains; fix section argument spacing; support current-template fragments; correct fragment visibility/capture.
2. **Make composition honestly compatible**: implement tag `it`, nested content and isolation opt-out; register/embed checked tag dependencies; validate fragment references and unknown sections.
3. **Close inexpensive language gaps**: add `with`, loop parity metadata, rich `when`, parameter defaults/conditional `let`, literal brace escaping and multi-pipe raw blocks.
4. **Choose and document a parser profile**: decide defaults for Qute tag recognition, standalone-line removal, optional end tags, textual aliases and non-strict output. A profile avoids silently breaking existing Radiant output while offering a clear migration target.
5. **Strengthen the checked path**: make all checked-template expressions type-check against Rust fields/accessors; add checked fragments and checked tag argument validation.
6. **Add ecosystem features only from demonstrated demand**: true streaming/deferred values, message-template parity, custom sections, cache and `eval`.

## Suggested compatibility contract

Radiant should avoid claiming byte-for-byte or feature-complete Qute compatibility. A useful, testable contract would be:

> Radiant supports a documented Qute-compatible core syntax profile. Templates in that profile have equivalent parsing, scope, control-flow, composition, missing/null and escaping behaviour, except for explicitly listed Rust safety differences.

Build a conformance fixture suite around that profile. Each fixture should contain one template, input value graph, expected output or error category, and expected source location. Run the same fixtures through Radiant's dynamic evaluator and checked path; where practical, run the source fixture against Qute too. This will also expose the currently unfulfilled design goal that checked and dynamic templates share one language.
